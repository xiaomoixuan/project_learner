这些问题由一个独立 Agent 先仅据原始简历、实际岗位职责和审查模块生成，题目冻结后才读取教材。以下保留原问题及该实例的最终实际回答、正文依据和结论边界，去掉私人记录路径、内部实例标识和哈希。回答用于检查教材是否教清，不是对真实项目实现的核验，也不应直接背成个人经历。

## 冻结问题与最终复答

### S-01 · CodeRelay首先为哪类研发协作任务解决什么困难？请用一个具体用户请求解释它的使用价值和完成任务的判断标准。

判定：通过 → 通过。

CodeRelay面向需要跨代码、文档和研发对象理解任务的研发人员。小林要求分析Atlas PR #42的CI失败、核对Issue #18并准备评论。平台连接当前差异、失败测试、业务约束和原需求，交付有来源的原因判断及草稿；完成标准是结论可核对、未知与建议分明、只准备时不发布。用户能少做跨系统搜集整理，并推进到可审阅成果。

正文依据：

- 1.1 研发人员为什么需要 CodeRelay：小林原需分别查文档、代码、Issue、PR和CI，困难是连接资料及核对版本。
- 1.2 从一个请求看项目要交付什么：共享客户端重试导致创建动作三次，Issue关注等待体验；成果是带证据的分析和评论草稿。
- 1.3 独立开发的目标与范围：成功标准为结果能用、重要结论可追溯、任务过程可控。

结论边界：Atlas及小林属于明确标注的教学重构；正文没有量化证明真实团队节省了多少时间。

### S-02 · 沿上述请求从进入平台到返回结果，解释CodeRelay各主要模块之间的信息流与职责分工；简历中的技术组件在这条链路中分别承担什么角色？

判定：通过 → 通过。

Next.js收集问题、仓库和会话，交给Python/FastAPI后端。后端补登录用户的权限和目标对象，规划模型提出计划；LangGraph依据共享状态推进分支，统一工具入口取得PR、Issue、CI资料，MCP提供外部能力接入。检索将Milvus语义召回与BM25关键词召回的文档补进证据。PostgreSQL保存工作区、状态、来源、会话及草稿。汇总形成有依据的解释和ActionDraft，SSE把持久化后的进展送到页面；用户确认后后端检查并提交、回填远端结果。

正文依据：

- 3.1 请求进入系统后，信息怎样增加：网页交后端；确定权限、计划、取得PR/Issue/CI、检索文档、汇总并草稿确认。
- 3.2 谁作决定，谁负责执行：LangGraph组织带共享记录的流程；模型提出判断，程序执行规则。
- 3.3 数据、证据和记忆各放在哪里：PostgreSQL保存准确记录和原文来源；Milvus按向量语义搜索，BM25补关键词路径。
- 4.2 MCP解决接入方式，服务规则继续约束执行；4.7：MCP扩展外部工具，仍走统一入口；SSE展示任务状态，状态先持久化。

结论边界：能解释单后端个人项目架构；不据此推定已部署分布式服务或大规模多租户能力。

### S-03 · 作为独立开发者，我怎样把信息分散的问题转成首版可交付功能，并据什么安排后续迭代顺序？请把我的主要工作讲成一条可执行的推进路径。

判定：通过 → 通过。

我先收集新人问答、评审PR和维护Issue/CI三类任务，按“先取得可靠证据，再增加协调和副作用”的顺序交付。我先做工作区、接入、索引、会话页面，跑通读资料到引用答案；再接Issue/PR/CI跨对象分析；随后增加可恢复状态、依赖调度、并发和失败限制；最后补确认执行、SSE和回归样例。一个后端保持统一部署，工具与索引按清晰边界维护；后续从真实瓶颈、失败和试用反馈安排迭代。

正文依据：

- 4.1 从只读闭环逐步做到任务平台：先问答、再PR/CI分析、再计划并行和草稿；分四阶段建设，统一后端降低维护负担。
- 5.4 交付内容与后续运行：同步、权限、工具失败和预算耗尽进入维护与下一轮任务。

结论边界：是正文允许的统一教学开发过程；不能当作新增的真实日期或团队经历。

### S-04 · CodeRelay的哪些请求值得使用多智能体协作，哪些请求适合更简单的处理路径？请说明采用多智能体的收益何时能够抵消协调成本。

判定：通过 → 通过。

单个文档问题直接检索、检查、回答即可。需要比较PR、CI、Issue并形成跨来源判断的请求，适合把有独立目标和工具权限的资料分支分开，再共享证据汇总。角色不一定用不同模型，也不必每次启动三个。收益来自各分支独立取证和可并行等待；成本是更多调用、上下文、状态和汇合检查。只有任务确实需要多源且存在独立工作时，才值得支付这些成本；纯串行依赖不会因加角色自然变快。

正文依据：

- 3.2 谁作决定，谁负责执行：规划、资料分析、汇总角色可用同模型；简单问答直接检索回答。
- 3.4 多智能体协作共享什么：不复制所有资料，每角色只读所需状态以控制干扰和成本。
- 4.3 依赖由“下一步必须知道什么”决定；5.3：独立分支可并行，依赖未齐不能提前；同条件比较耗时、调用量与完整性。
- 6.4 换一个条件继续判断：简单问题不必完整多角色计划。

结论边界：正文给出选择原则，未提供测得的并行加速比；不能宣称所有复杂请求均更快。

### S-05 · 从一个子任务准备调用工具开始，说明统一工具体系怎样把模型提出的调用变成可执行请求，并在参数无效时阻止错误进入实际执行。

判定：通过 → 通过。

我先给工具明确的目的、输入对象和限制，例如CI日志工具需要已经选定的仓库、运行和任务。模型提出调用后统一入口检查对象完整性、工作区归属、登录用户权限及预算，再允许实际访问。缺参数不能绕过入口执行，调度将其变成补信息而非网络重试。返回结果按约定整理证据或区分无权限、对象不存在、临时错误、内容不足，下一步才能采用对应处理。

正文依据：

- 4.2 工具要让模型知道什么时候用，也让程序知道怎样检查：日志工具只读已选运行；入口检查对象完整、工作区、权限和调用限制，失败分类。
- 3.2 谁作决定，谁负责执行：模型提出调用，程序检查参数、越权、预算与写入确认后访问。
- 4.3 失败怎样改变计划：参数不完整或权限不足需要补信息或停止分支。

结论边界：正文足以说明校验顺序与作用，不需额外猜测实际JSON Schema或函数签名。

### S-06 · MCP在CodeRelay里怎样扩展调用能力？请说明它与平台内部工具接口的衔接边界，以及接入一个新工具需要解决的核心适配问题。

判定：通过 → 通过。

MCP为CodeRelay与外部研发工具服务提供通用的发现和调用边界。内部规划看到统一工具说明，实际调用即使来自MCP也要经过平台入口，不能把外部服务等同于可信授权者。我接新工具时补目的与限制、参数和对象适配、返回证据约定、错误分类，再纳入身份、超时和写入检查。外部PR正文中的指令仍是数据，不能借接入协议提升权限。统一适配减少每角色重复校验，代价是新连接器要先遵守这些契约。

正文依据：

- 4.2 MCP解决接入方式，服务规则继续约束执行：MCP能发现与调用外部工具；调用继续检查身份、参数、超时、写入；新增工具需描述、返回约定、错误分类。

结论边界：没有扩展到协议版本、传输细节或未声明的服务端实现。

### S-07 · 工具返回结果后，Agent怎样判断这次调用是否为当前问题提供了可用证据，并决定继续检索、交给后续任务或结束回答？

判定：通过 → 通过。

工具结束不等于任务已有答案。CI日志先形成当前提交下“预期一次、实际三次”的观察和来源，并把线上问题根因仍待核保留下来；PR比较任务据此启动。程序先核对引用是否属于本次项目和版本，模型辅助比较结论与原文是否保留条件。若必要条件缺失，继续定向取证或回到生成修答；预算内仍不足就收缩结论并交付可支持的部分。只有目标问题所需联系均有证据，才结束对应判断；次要资料缺失可标明范围后结束局部结果。

正文依据：

- 4.2 一次完整的工具交接：观察、来源、未决问题写入共享状态，不能把测试现象扩大为线上结论。
- 4.4 从片段变成回答还需要判断：程序核引用范围，独立模型调用核条件和支持；补查、改答或收缩结论均用剩余预算。
- 4.3 失败怎样改变计划：必要资料缺失时判断未完成，其他独立分支可完成并交付部分结果。

结论边界：正文未承诺检查模型永不漏判；高风险规则另做回归，写入仍由程序授权。

### S-08 · 面对一个同时需要代码、Issue/PR和CI证据的复杂请求，怎样拆出有依赖关系的子任务，并据此判断哪些任务可以进入最多3路的并行执行？

判定：通过 → 通过。

我先把产物定为失败分析、需求关联和评论草稿。读取PR与Issue只需已知对象，可先并行；CI要等PR当前提交确定，才能选对应运行。PR完成后CI可启动，不必等Issue。导出规则检索使用PR/CI识别出的创建动作和重试信息；综合分析等核心证据，评论等综合分析。调度只从前提满足的工作中取任务，同时运行不超过三项，第四个就绪项等空位。不能为了占满三路把依赖未齐的CI或评论提前。

正文依据：

- 4.3 依赖由“下一步必须知道什么”决定：工作表给PR、Issue、CI、规则、综合和评论各自前提；PR与Issue并行，CI依赖当前提交，最多3个子任务。

结论边界：代码证据可由PR差异或定向代码读取取得，正文不要求任何场景都额外启动独立代码角色。

### S-09 · LangGraph如何承载这个执行过程的任务状态与状态转换，使规划、工具执行和结束判断能围绕同一个任务进度工作？

判定：通过 → 通过。

LangGraph把工作组织为节点和允许的转移，节点围绕同一任务记录决策。计划先经程序检查循环依赖、未知工具、并发和自动写入等问题，再保存。子任务经历等待前提、可运行、执行中、成功或失败，等待用户和等待确认另有状态；PostgreSQL保存计划、进度、证据及未决问题。分支结果回写后，图依据这些事实选继续、等输入、汇总或结束。中断后读取已保存进度，先核对结果未明的外部操作再恢复，避免从原句重做全部步骤。

正文依据：

- 3.2 谁作决定，谁负责执行：节点做工作、边约束去向，依据共享记录选择继续等待或结束。
- 3.4 多智能体协作共享什么：共享目标、计划、进度、引用、发现和未决问题。
- 4.3 模型提出的计划要经过检查：状态保存在PostgreSQL，LangGraph按状态推进，中断恢复先核对不确定的外部操作。

结论边界：这是正文提供的状态与控制机制，不声称已教具体框架API或数据库事务实现。

### S-10 · 并行任务得到彼此冲突或部分缺失的结论时，最终汇总应怎样处理这些结果，才能避免把并行完成误当作用户任务已经完成？

判定：通过 → 通过。

各分支按自己的子任务写结果，共享状态保留全部证据，不能让后结束的分支覆盖前者。冲突保留后安排针对性核查，例如核对文档的安全条件与代码当前是否具备防重复；不能多数投票就抹掉条件。汇总先读取分支成功、失败或取消及证据缺口，再判断用户问题的哪些部分已可回答。缺CI关键观察时失败原因仍未完成，但Issue诉求可独立交付。最终可以是带明确未完成项的部分成果；所有分支停止并不自动等于全部目标已完成。

正文依据：

- 3.4 多智能体协作共享什么：分支结果各自汇入，保存来源，不能覆盖另一个结论；冲突保留并针对核查。
- 4.3 失败怎样改变计划：汇总读取分支终态，交付能支持的部分，保留原目标未完成部分。

结论边界：未引入正文没有的仲裁算法；文档允许有条件重试与代码缺条件可能是待核差异，并不必然是事实互相矛盾。

### S-11 · 一个子任务持续超时或反复拿到无效结果时，怎样利用失败反馈决定下一次尝试，并由什么条件保证有限重规划最终停止？

判定：通过 → 通过。

我为单次调用、子任务和整体设置时间预算。临时读取错误先在剩余预算内做有限间隔重试；缺参数或权限则补输入或停分支。日志已清理属于计划依据变化，反馈具体缺口后改读测试报告、PR差异和测试源码。每任务最多两次计划修订，同时受总调用量与总时间限制；并行发起前共享扣用同一额度。已失败的同对象、问题和参数若没有新增信息，不允许把措辞改一下再调。替代资料仍不足就返回证据限制或局部结果，不无限等待。

正文依据：

- 4.3 失败怎样改变计划：三层时间预算，临时读取有限重试，日志清理改路径；最多两次修订并限调用与时间，同参失败无新信息不得重复，共享预算预先计入。

结论边界：两次为教材重构设置，非原简历可独立证实的真实配置；写入结果未知采用4.6专门恢复策略。

### S-12 · 代码、文档等原始材料怎样变成能够检索并追溯来源的知识；当材料更新时，怎样避免旧内容继续被当作当前证据？

判定：通过 → 通过。

我把文档按标题和主题切片，保留条件与原因在同一片段，代码按职责相关范围组织；片段带仓库、原文、文件位置、版本和更新时间，原文与来源存PostgreSQL，语义向量进Milvus，另有BM25路径。检索前先筛当前用户可见项目和适用版本。更新时旧片段退出当前有效索引，新片段与新来源对应；旧结论或记忆按版本标过期，当前回答不能沿用旧事实。引用因此可以回到明确资料。

正文依据：

- 3.3 数据、证据和记忆各放在哪里：PostgreSQL保存原文来源，Milvus按向量搜索，另有BM25。
- 4.4 先让资料片段保留原本意思：标题主题切分、代码位置与版本、过滤当前权限适用版本；更新时原片段退出有效索引。
- 4.5 长期记忆保留值得跨会话使用的内容：新规则启用后，引用旧规则的长期记录过期。
- 6.2 当前不足与下一步：索引和代码变化有时间差，需完善变更触发的增量更新。

结论边界：正文说明更新原则，也承认同步有时间差；不能推定已实现实时无缝增量更新。

### S-13 · CodeRelay一次混合检索怎样把向量召回和BM25的结果组织成最终交给生成环节的候选证据？请解释两类召回为何有互补价值。

判定：通过 → 通过。

向量把不同表达映到相近含义，适合用户的“自动再发一次”与文档恢复策略的表达差异；BM25按词出现和稀有程度抓住创建接口、测试名、错误码等精确线索。两路各取候选，按片段身份去重，再按各自名次合并而非直接相加原始分数。导出专项规则若在语义第二、关键词第一，可比仅语义靠前的通用重试说明更受支持。最后取覆盖关键条件、不过度重复且放得进上下文的Top-K片段，交给回答模型。

正文依据：

- 3.3 数据、证据和记忆各放在哪里：向量处理语义近似，BM25利用词出现和常见程度。
- 4.4 两条搜索怎样一起工作：两路候选按身份去重、名次融合RRF，再选择Top-K；以通用重试和专项规则说明排名贡献。

结论边界：正文不提供RRF常数与公式，问题只要求解释机制，不需要增造数值排名。

### S-14 · CodeRelay实际需要记住哪些会话信息，怎样决定保存、读取和失效的范围？请讲清会话记忆与检索知识各自负责什么。

### S-27 · 最多3路并行和有限重规划应怎样兼顾任务质量、等待时间与资源消耗；在什么观测结果下需要调整这些限制？
