# 让岗位要求改变讲解重心

先认识同一个完整项目，再根据实际JD确定哪些工作必须讲深。岗位适配体现在功能解释、方案选择和个人贡献中，不是给章节贴JD关键词。无JD时按已知求职方向，不补造企业要求。

把岗位能力接到项目中的具体任务：在哪里需要它，怎样起作用，作者作过什么决定，读者要能解释到什么程度。没有合理业务来源的能力不硬加；直接相邻的扩展可以教清思路，但不声称已经真实实施。

| 岗位方向 | 应在项目中讲透的关系 |
| --- | --- |
| Agent / AI应用工程 | 用户需求怎样进入系统，模型、规则、工具与协作角色怎样分工，信息和记忆怎样支持决策，任务怎样推进，能力怎样进入可用业务并被验证 |
| 产品 / AI产品 | 用户任务怎样转为功能和规则，方案如何取舍，交互怎样承接系统能力，反馈与指标怎样支持迭代 |
| 后端 / 平台 | 业务需求怎样转为服务和数据设计，各部分怎样协作，可靠性问题怎样影响方案，怎样验证与交付 |
| 算法 / 数据 | 问题怎样转为数据与方法选择，实验怎样比较方案，错误怎样定位，结论怎样进入业务决定 |
| 前端 / 设计 | 用户过程怎样转为界面与交互，状态怎样反馈，设计依据和验证怎样产生，如何与系统和其他角色配合 |
| 研究 / 运营 | 目标怎样转为方法与执行安排，观察怎样支持解释，资源与反馈怎样改变方案和结果 |

上表用于选择深度，不是知识清单。工程岗位要学会解释设计与实施思路，不意味着整本手册必须像代码教程；产品岗位也不能只讲价值而省略真正影响功能的机制。

我的贡献按实际角色表达，背景和其他成员职责保留。先学习项目，再提炼岗位相关的讲述；不能靠夸大规模、角色或结果来匹配JD。
