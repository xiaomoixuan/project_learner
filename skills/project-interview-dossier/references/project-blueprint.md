# 用一份轻量底稿补建完整项目

底稿用于让作者在同一情境中写作，不能发送给盲问代理，也不要求用户批准。简历提供线索和约束，不是完整设计书；沉默不是“没做过”的证据。

## 联合理解线索

结合公司/行业、岗位、时间、业务动作、系统机制和结果，判断是已有产品优化、客户交付、从零开发、运营、研究还是其他工作。不要只凭一个技术词推断整个项目，也不要因为简历没写实施或上线就判定没有。只有用户明确给出的限制才构成硬边界。

例如简历同时提到客户工单、线上日志、版本验证，通常可构建“已有服务正在优化”的情境。仍须补清谁是客户、谁在使用、服务如何运行、具体哪里出问题，以及我的任务如何介入；不能把它缩成一批评测题，也不能把全平台开发都归给实习生。

## 建立相容的项目世界

用简短叙述回答：

- 谁发起或购买，谁使用，解决什么任务；用户从哪里进入，输入什么，得到什么。
- 开始前已有的服务与系统怎样工作，什么问题触发这次改进。
- 本次目标、阶段和交付是什么，哪些上下游影响它。
- 团队和我怎样分工，任务从哪里来，周期、权限和资源是否支持这些工作。
- 关键业务规则和名称怎样统一；成果怎样被接收和使用。

未给的内容主动选择合理方案，必要时补具体团队、版本、业务规则、协作和交付过程。选择应服务完整教学，不需要假造繁琐审批。材料性质按主Skill统一说明，底稿使用同一套明确情境，不反复“可能、待确认”。

## 走通两个过程

产品运行：使用触发→输入→人或系统的处理→结果→异常及维护。研究等非软件项目讲成果如何被使用，不强造App。

项目推进：原问题怎样被发现、任务怎样确定、怎样设计和执行、材料怎样流转、如何验证、谁据此作决定、怎样交付并继续迭代。不强迫已有产品重走从零建设过程，也不把推进节点硬变成阅读章节。

选一个有代表性的业务对象连接二者，让读者看见用户得到服务，以及围绕同一问题我怎样推动改进。关键机制不同的分支另选必要例子，不强求所有知识挤进一个故事。

## 形成能力与学习依赖

确定主要功能怎样被使用、怎样在系统或工作过程中完成，以及我怎样把它做出来。由这些过程推导读者需要的概念、选择、难点和结果，不逐句解释简历，不为每项内容强造一份日志或操作材料。

结合真实JD决定哪些设计必须深入，哪些上下游只需交代。相同机制放在一个主要位置讲透，再说明它与其他功能的关系。统一人物、对象、阶段和结果，避免为回答一道追问临时造出另一套项目。

底稿服务于写作，不是正文目录或答题索引。缺少实施材料时，按主Skill补建相容方案，解释决策与过程。
