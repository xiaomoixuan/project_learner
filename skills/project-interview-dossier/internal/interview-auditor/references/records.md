# 问题冻结与验收记录契约

使用模块内的两份 JSON 模板。它们是空骨架，空字符串、空依据与 null 状态不能直接作为一次已完成审查交付。实际输出使用 UTF-8 JSON，避免把说明写进 JSON 注释。

## 文件和版本

- 每个镜头保存自己的 `questions.json`、`ledger-v1.json`、`ledger-v2.json` 等。阶段末由主 Skill 汇总，代理之间不互相覆盖文件。追加题写成新问题版本 `questions-v2.json`，包含全部原题与新题，并通过 `previous_questions` 引用前次问题文件；旧文件不覆盖。
- `case_id` 是本次教材案例 ID，`lens` 为 A/B/C 或明确的新增镜头。题集和账本的 `auditor_id` 固定为最初独立出题实例的真实 ID，接替或追加题均不改写该归属。账本可选 `reviewer_id` 记录本轮实际检查者；省略或为 null 时等于 `auditor_id`，因此既有 schema 1.0 同人初轮记录继续有效。
- 实际检查者与前次账本的检查者不同（首轮则与 `auditor_id` 不同）时，账本必须填写 `handoff: {"from_reviewer_id": "前任真实ID", "to_reviewer_id": "本轮真实ID", "reason": "接替原因"}`。同一检查者继续复查时 `handoff` 省略或为 null；之前的交接仍由账本链保留。三个镜头的初始出题实例和本轮实际检查者分别必须互不相同。身份字段只供追溯，不能证明真实上下文隔离。
- `input_sha256` 为原始 `input.md` 文件字节的 SHA-256，不把模块路径、镜头指令或其他提示字符串混入。输入文件仅包含原始简历原文/忠实转录及用户实际提供的JD，不能混入作者背景、方向推断、范围摘要或知识清单；模块、镜头与用户选定项目属于系统调度指令，不参与该哈希。没有JD不补企业要求。
- 新教材不添加审查索引标记或摘要，按整份教材文件计算 `draft_sha256`；完整索引与账本另存配套文件。以下标记规则只用于兼容已有带尾部索引的历史教材。
- `draft_sha256` 为受验正文中 `<!-- INTERVIEW_AUDIT_INDEX -->` 标记之前的原始 UTF-8 字节的 SHA-256；无该标记则算全文件。标记之前不额外增删空白，不做换行标准化或 trim。标记后的末尾覆盖索引不进入该哈希，避免索引写入哈希又改变自身受验版本。question 阶段该字段为 null。正文依赖外置图表时，同时保留它们的版本/哈希清单，不能在复查之间无记录更换材料。
- ledger 的 `questions_sha256` 为本次受验问题 JSON 文件原始字节的 SHA-256，用于绑定冻结题集。追加问题之后使用新问题文件的哈希，并保存它与前版本的关系。
- `previous_ledger` 指向前次实际记录，首轮为 null；首轮 `phase` 为 `review`，有前次账本的后续轮为 `recheck`。新增 ledger 不覆盖旧文件。问题版本链和账本链必须可读取、无循环且维持相同案例、镜头、输入哈希与出题归属；旧账本绑定的问题哈希必须仍能在完整问题版本链中找到，不能回退到较早题集。
- `previous_questions`、`previous_ledger` 和每项 `history.ledger` 的相对路径，均以**含有该字段的 JSON 文件所在目录**解析，不以命令工作目录或其他被引用文件为基准。允许绝对路径；移动记录目录时必须相应更新引用并重新计算依赖文件哈希，不能漏掉历史版本。

## 每个子问独立占一个 questions 元素

| 字段 | 含义 |
| --- | --- |
| `id` | 全局稳定子问 ID，例如 `A-02.1`；不可重用、重排后改号或静默删除 |
| `chain_id` / `parent_id` | 连续追问链与前置子问；首问 parent_id 为 null |
| `question` | 可独立判定的完整问题；包含两个独立要求时拆成两个 ID |
| `basis` | 来源、定位及为什么需要问；来源是原始输入、用户原题或后来发现的依赖，不能只有“常见面试题” |
| `scope` | `in_scope` 或 `boundary`，附理由；boundary 仍须回答正文中的边界与替代路径 |
| `origin` | `type` 为 `blind_question` 或 `review_followup`；前者的 `discovered_from` 为 null，后者填发现它的已有问题 ID。可选 `authored_by` 省略或为 null 时等于题集 `auditor_id`；接替者追加的新题必须填其真实 ID，旧题不补改该字段 |

question 阶段冻结这些字段和输入哈希。主 Skill 可做跨镜头覆盖检查；如发现遗漏，应把原输入中的缺口交还镜头追加问题，而不是给出作者希望被问的问题及答案。用户原题在 `basis.source_id` 保存原 ID，多个子问各自保留。

所有模板中的非可选字段均须存在，并使用示例所示类型。`basis` 是非空对象数组，元素包含 `source`、可为 null 的 `source_id`、`locator`、`reason`；`scope` 包含合法 `type` 及非空 `reason`。首个题集仅包含盲问；看过正文后的追加题必须保留前题集链，且在首次包含它的账本中由实际作者作答。`origin.authored_by` 在两份模板中用 null 表示默认原出题者，不要求给旧文件补字段。

问题措辞确需纠错时，保留旧问题与纠错原因，用新 ID 关联；原回答义务必须有明确承接，不得把“请执行”改成“请列概念”。适用性争议也保留原判定与改判依据，由原检查者基于输入和正文边界复查。作者不能单方面取消问题。

## review / recheck 的 answers 数组

ledger 使用平铺 `answers` 数组，元素与 questions 中的原子子问按 `id` 一一对应，并保留原文 `question`、`basis`、`scope` 和来源链。不要在某个问题下再嵌套多个未分别判定的子问题。每个元素追加以下字段：

| 字段 | 含义 |
| --- | --- |
| `answer` | 仅据正文写出的实际答案、步骤或小交付；涉及我的职责使用第一人称 |
| `evidence` | 正文标题/锚点与实际句意或短摘录；不能仅填“第 3 章” |
| `derivation` | 使用的前提与逻辑/算术步骤、需要新增但正文没有的关键前提 |
| `boundary` | 当前材料可支持的结论与不能推定的内容；范围外题还要说明正文边界和替代路径 |
| `status` | 仅允许通过、过浅、缺失、冲突；解释以主验收协议为准 |
| `gap` | 非通过时明确停在哪一步；通过时为空字符串，完整判定依据仍写在答案与证据中 |
| `repair` | 主作者需修改或已经修改的正文位置、关联引用和动作；代理不直接修改正文 |
| `recheck` | 本次复验做了什么、受影响旧通过题是否已重验；首次审查时说明首次执行结果 |
| `history` | 按时间从早到晚保存当前子问之前每一轮的判定，初次出现为 `[]`；统一结构及继承规则见下文 |

`derivation.new_premises` 非空且其中包含回答所需关键前提时不得通过。范围外问题的通过答案须有正文边界依据及适当替代路径，不能只写“不适用”。专业知识可以帮助发现错误，不能把检查者的专业知识当成读者已在正文中获得的规则。

`derivation` 必须有字符串数组 `premises`、`steps`、`new_premises`；后者只记录回答所需而正文没有的关键前提。`repair` 必须有字符串数组 `locations`、`related_references` 及字符串 `action`，初轮没有修补时可为空。`evidence` 是含 `locator`、`content` 的对象数组，未通过时允许为空，通过时至少有一项。`recheck` 始终填写本轮实际执行情况；失败转通过时 `repair.action` 与 `recheck` 都不得为空。脚本只核对这些结构与记录是否存在，不判断动作是否足以修好正文。

每项历史使用以下结构，不增加另一套状态格式：

```json
{"draft_sha256": "前次正文的64位SHA-256", "status": "缺失", "gap": "前次原断点", "ledger": "ledger-v1.json"}
```

同一子问在新账本中保留前一账本的完整 `history`，再追加指向前一账本的上述快照；`draft_sha256`、`status`、`gap` 必须逐值等于前次实际记录。即使之前已通过，也追加本轮前的快照；新增题首次出现时 `history` 为 `[]`。若新旧账本位于不同目录，继承历史的路径可以改写，但必须仍解析到同一旧文件。不得省略失败轮次、修改旧状态或丢掉此前已有的子问。

## 主 Skill 汇总时的完整性核对

1. 三个镜头实际存在，初始出题实例、实际检查者与隔离方式有记录，必要交接衔接前任；每份 ledger 的输入哈希一致。
2. ledger 的 `questions_sha256` 与实际受验问题文件匹配；冻结与追加问题的 ID 逐一存在，旧版本中的同 ID 原文字段一致，原题/子问义务未被省略，没有通过去重丢失记录。
3. 最终 ledger 全部指向同一最终正文哈希，每个子问都有实际答案、具体正文依据、推导边界和四状态。
4. 每个适用子问及边界回答均为通过；前账本和逐题完整历史可读、相符且无断链；失败转通过有正文修补与复查，受影响旧通过题也已重验。
5. 机器检查只核对字段类型与完整性、冻结字段一致性、ID/版本/历史引用和状态。内容是否正确、证据是否真的支持答案、修补是否实际完成及范围是否被偷换，仍需阅读和执行判断。

没有固定问题数量、平均分阈值或最多三轮后放行的规则。若资源中断，保存问题和未通过项，向主 Skill 报告未完成；不能以记录格式正确替代教学验收。

可使用随包提供的 [check_audit.py](../../../scripts/check_audit.py) 核对记录完整性：传入 `--input`、`--draft`、三个镜头的 `--questions` 文件与 `--ledgers` 文件。中间轮加 `--allow-incomplete` 只查记录完整性；最终轮不加该参数，任何未通过都会返回失败。脚本不评判答案正确性，也不能凭填写的实例 ID 证明真正的上下文隔离。

## 后补JD的独立批次

真实JD后补时另存原简历与该JD的新input文件，新批次采用不同case_id和新题ID；原批次与原题完整保留。每批继续使用既有schema 1.0，不把不同输入哈希的文件接进同一previous_questions/previous_ledger链。各批分别用check_audit.py对同一最终正文检查，汇总时任何批次未通过都不能宣布完成。作者补教后，各批原问题都要对当前正文核对，不沿用旧版通过。
